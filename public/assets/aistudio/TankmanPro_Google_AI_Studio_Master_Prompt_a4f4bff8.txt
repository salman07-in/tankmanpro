CORE BUSINESS REQUIREMENTS
There are three distinct role-based experiences:
1. Customer storefront/account: browse published categories/services, select city or six-digit PIN code, see actual area coverage, view prices, select variants/add-ons, schedule a service, enter address, apply coupons, pay using a configured method, and view their own bookings.
2. Main Admin: manage cities, PIN codes, coverage, categories, services, variants, add-ons, base/city/vendor prices, vendors, vendor-service coverage, schedules/capacity, coupons, orders, assignments/reassignments, refunds via verified payment flow, content, policies, settings, reports and audit logs. All operational values must be manageable without code changes.
3. Vendor Portal: separate login at https://partner.tankmanpro.com/login (with `/vendor/login` as a preview fallback); vendors can see and manage only orders assigned to their own authenticated UID. Main Admin uses https://admin.tankmanpro.com/login (with `/admin/login` fallback). Neither portal is linked anywhere in the public storefront. They can accept/reject assigned work, provide rejection reason, and update allowed work status. They cannot read other vendors' orders, access global customers, change prices, alter payment/refund state, assign themselves jobs or enter the Admin console.

CITY / PIN CODE ROUTING
- Customer chooses city or enters a valid six-digit Indian PIN code.
- Resolve PIN to Admin-configured, active service area. Never trust client-supplied city without server verification.
- Filter services and vendor offers to active service area and service coverage.
- Admin can define which vendors serve which cities/areas and services, vendor working schedule, capacity and active status.
- If no matching area/vendor is available, do not create a fake confirmed booking or collect payment; show a clear unavailable state and optionally collect an opt-in waitlist request.
- Assignment must happen server-side. Do not accept arbitrary vendor UID from the client.

PRICING REQUIREMENTS — CRITICAL
Support both modes per service/city:
A. CITY-FIXED / AUTO-ASSIGN: customer sees one Admin-configured city price; backend assigns an eligible vendor via configured round-robin/least-active strategy.
B. VENDOR-OFFER / CUSTOMER-SELECTS: customer sees eligible Admin-configured vendor-specific prices for that service/city and selects an offer. Keep that vendor and price attached to the checkout/booking; do not silently substitute another vendor.
Price precedence where enabled: vendor + service + city + variant override > city + service + variant override > base price. If no valid price/policy exists, fail safely and ask Admin to configure it. Admin, not vendor, controls V1 customer prices. Store prices as integer paise. At checkout, recalculate every amount server-side and snapshot all prices/discounts on the booking. A stale or tampered client quote must be rejected or reconfirmed.

SERVICE MANAGEMENT
Admin CRUD for categories, services, descriptions, slugs, images, inclusions/exclusions, duration, variants/packages, add-ons, dynamic service questions, published/draft/archive status, city coverage and SEO fields. Archived services remain in old booking snapshots but cannot be booked for new orders. Customer catalogue reads only published records.

COUPONS
Admin can create percentage or fixed coupons with validity dates, max discount, minimum subtotal, global and per-customer use limits, active flag, city/service/category restrictions, new-customer condition, non-stackable default and redemption log. Backend is the source of truth; never trust a frontend-discount amount. Check and consume redemption eligibility atomically at booking confirmation. Abandoned or failed payments must not permanently consume a coupon unless the configured policy says so.

BOOKING FLOW
1. Location check.
2. Choose category/service/variant/add-ons.
3. Show city price or eligible vendor offers.
4. Select date/time slot from configured availability.
5. Select/add service address and contact details.
6. Apply coupon and recalculate.
7. Show transparent subtotal, discount, configured tax/fees, total, policies and payment method.
8. Create a short-lived slot/booking hold server-side to avoid overbooking.
9. Create Razorpay order server-side if online payment is enabled.
10. Verify payment signature on server; process webhook with exact raw body, signature verification and idempotency. Never trust frontend redirect alone.
11. Confirm booking and finalize assignment only according to the payment/booking policy. Release expired holds; if a selected vendor/slot becomes unavailable, ask customer to choose again rather than silently changing price/provider.
12. Notify customer/vendor/Admin if delivery providers are configured.
13. Vendor accepts/rejects then updates permitted job status; Admin can reassign with audit log.

BOOKING / PAYMENT / JOB STATES
Keep separate fields for assignment status, job status and payment status. Suggested assignment states: unassigned, assigned, accepted, rejected, reassignment_required. Suggested job states: assigned, accepted, in_progress, completed, cancelled. Payment states: pending, authorized/created where applicable, paid, failed, refund_pending, refunded, partial_refund where supported.
